# Reglas propuestas de calidad de datos

Estado: contrato **propuesto**, pendiente de comprobar durante la implementación. R = requisito del [README](README.md); D = decisión para esta prueba; S = supuesto por validar. La arquitectura está en [TECH_SPEC](TECH_SPEC.md) y las tareas en [IMPLEMENTATION_PLAN](IMPLEMENTATION_PLAN.md). No cambiar una regla en código sin actualizar este documento y sus tests.

Durante la planificación se inspeccionaron cabeceras y algunos registros de CSV, XML y stock; solo se recorrieron los valores distintos de estado/canal. F2 añadió la lectura completa del catálogo, sin tarifas ni carga en BD; su evidencia parcial consta en SOLUCION. No se ha ejecutado el ETL completo ni obtenido conteos finales de productos. El catálogo tiene 11 columnas (`sku, ean, nombre, marca, categoria, precio_coste, pvp_recomendado, iva, peso_kg, fecha_alta, descripcion`); pedidos tiene 9 (`id_pedido, fecha_pedido, cliente, canal, estado, sku, cantidad, precio_unitario, descuento_linea`).

## Principios y acciones

- No inventar datos ni reconstruir identificadores perdidos.
- Un valor desconocido es `NULL`, no `0`.
- Dinero y descuentos se parsean desde texto a `Decimal`; nunca se calculan con `float`.
- Una decisión que descarta una fila o campo deja fuente, localizador y motivo.

**Normalizar** conserva el significado; **rechazar fila** excluye la entidad; **descartar campo** conserva la entidad con ese campo `NULL`; **deduplicar** conserva una ocurrencia; **avisar** conserva el dato con incidencia; **fallar ejecución** impide publicar el lote. El mínimo operativo es: cabecera/archivo ilegible → falla ejecución; fila incorrecta → rechazo; API incompleta tras reintentos → falla ejecución. Un fallo de MySQL revierte la carga. No se diseña aquí una recuperación automática adicional.

## Matriz de decisiones

| Caso y fuente | Regla D propuesta | Acción y motivo |
| --- | --- | --- |
| Catálogo CSV | Latin-1, separador `;`, lector CSV que respete comillas. | Decodificar; archivo ilegible o cabecera incorrecta → fallar (`INVALID_ENCODING`/`INVALID_HEADER`). |
| Pedidos CSV | UTF-8 con BOM (`utf-8-sig`), separador `,`, comillas que pueden contener comas. | Igual; no usar `split`. |
| Tarifas XML | UTF-8 y parser XML; la excepción por SKU tiene prioridad absoluta. | XML ilegible → fallar (`INVALID_XML`). |
| Fila CSV con más/menos columnas | Exigir 11 columnas de catálogo y 9 de pedidos; no desplazar campos. | Rechazar fila (`INVALID_COLUMN_COUNT`), continuar. Si el parser no puede recuperar límites de registros, fallar (`INVALID_CSV`). |
| Vacío, `N/D`, `NULL`, `-`, `n/a` | Tras trim/casefold, solo el token completo significa ausencia; un guion dentro de un SKU no. | `NULL` en campo opcional; rechazar si es obligatorio (`MISSING_REQUIRED_FIELD`). Descuento de línea vacío = 0 con aviso. |
| Textos, SKU e ID | Normalizar Unicode NFC, trim y espacios; comparar marca/categoría sin distinguir mayúsculas, conservando tildes. SKU/ID en mayúsculas sin quitar guiones ni rellenar ceros. | Conservar etiqueta legible; identificador vacío/inválido → rechazo (`INVALID_IDENTIFIER`). |
| Precio/coste/PVP | Aceptar coma o punto decimal, miles agrupados inequívocos y `€`/`EUR`; interpretar con `Decimal`. Precio obligatorio inválido o <=0 se rechaza. | `INVALID_PRICE`, `AMBIGUOUS_NUMBER` o `NON_POSITIVE_PRICE`. Una excepción XML válida puede sustituir un coste CSV inválido, registrando el descarte de ese campo. |
| IVA/peso/fecha de alta | Opcionales; centinela → `NULL`. Valor inválido → `NULL` con incidencia. Peso `0` no se interpreta como desconocido. | `INVALID_TAX`, `INVALID_WEIGHT`, `INVALID_DATE`; no inventar una fecha ni un IVA cero. |
| EAN | Quitar espacios/comillas exteriores o un apóstrofo inicial de Excel; validar EAN-8/EAN-13 y dígito de control. Vacío o inválido → `NULL`; nunca reconstruir notación científica ni prefijar ceros. | Producto válido con EAN descartado (`INVALID_EAN`/`UNSAFE_SCIENTIFIC_EAN`); ausencia sin dato inventado. |
| Duplicado de catálogo | Filas idénticas: una sola. Mismo SKU con valores distintos: **primera fila válida en orden del fichero**; registrar las demás. No hay timestamp para inferir la más reciente. | `EXACT_DUPLICATE` o `CONFLICTING_PRODUCT_SKU`, con localizador de ganadora/perdedora. |
| Tarifas coincidentes | Excepción válida manda; si no, coste × (1 − descuento categoría − descuento marca). Reglas repetidas idénticas se deduplican; valores distintos para la misma clave no tienen ganador justificable. | Registrar `CONFLICTING_TARIFF` y fallar la ejecución antes de publicar costes. No aplicar `<PorVolumen>`, portes ni plazo de pago sin compra conocida. |
| Fechas | Aceptar ISO, `dd/mm/yyyy`, `dd-mm-yyyy`, `yyyy/mm/dd`, con hora cuando exista. Parseo estricto; pedido se agrupa por día. | Alta opcional inválida → campo `NULL`; fecha de pedido ausente se hereda solo si otra fila del mismo pedido aporta un único día inequívoco; si no, rechazar pedido (`INVALID_DATE`/`MISSING_ORDER_DATE`). |
| Descuento de línea | `10%`, `10` y `0,1` → 0.10. Ratio válido [0,1]; vacío → 0 con aviso. | Rechazar línea si no se puede interpretar (`INVALID_DISCOUNT`); no adivinar otra escala. |
| Estados y canales | Canonizar con las etiquetas observadas abajo; no mapear desconocidos por parecido. | Estado/canal desconocido → rechazar pedido (`UNKNOWN_ORDER_STATUS`/`UNKNOWN_CHANNEL`). |
| Cantidades | Aceptar enteros exactos, incluso `2,0` → 2; cero o fracción real se rechaza. Negativas solo con estado DEVUELTO; conservar signo. | `INVALID_QUANTITY`/`INVALID_QUANTITY_FOR_STATUS`; no redondear. |
| Cabecera de pedido | Agrupar por `id_pedido`. Vacíos pueden heredar un único valor válido del grupo; valores no vacíos contradictorios no se eligen arbitrariamente. | Rechazar pedido y sus líneas (`CONFLICTING_ORDER_HEADER`) si no hay cabecera coherente. |
| Líneas repetidas | Sin ID de línea de origen: deduplicar firma canónica `(pedido, SKU, cantidad, precio, descuento)`; líneas distintas se conservan. | `DUPLICATE_ORDER_LINE`; dos líneas legítimas idénticas son indistinguibles, limitación visible. |
| SKU de pedido sin catálogo | Crear producto histórico mínimo por SKU para mantener FK; atributos desconocidos `NULL`. | Conservar línea; aviso `HISTORICAL_PRODUCT_CREATED`. |
| SKU solo en stock | Stock no crea producto comercial ni histórico. | Rechazar observación (`UNKNOWN_PRODUCT_SKU`). |
| Catálogo sin stock observado | Ausencia de dato no equivale a cantidad cero. | Producto con `stock_total=NULL`; cero solo si se observó explícitamente (`STOCK_NOT_OBSERVED`). |
| Stock por almacén | Sumar `quantity` de observaciones válidas por almacén; conservar `reserved` separado. `quantity`/`reserved` negativos o fecha inválida → rechazar observación. `reserved > quantity` **no se rechaza por defecto**: avisar y revisar significado. | `INVALID_STOCK`/`INVALID_DATE` o aviso `RESERVED_EXCEEDS_QUANTITY`. La métrica inicial es stock físico, no disponibilidad. |
| Registros repetidos de stock | Para mismo SKU/almacén, usar el `updated_at` más reciente; conflicto de mismo instante → aviso y total del SKU desconocido. | `CONFLICTING_STOCK`; no sumar dos versiones del mismo almacén. |
| API 500/429/timeout | Reintentos acotados; respetar `Retry-After` cuando exista. Autenticación 401 no se reintenta. Recorrer todas las páginas. | Si no se completa la extracción, fallar ejecución (`STOCK_FETCH_FAILED`); no publicar stock parcial. |

**Concreción F2 del catálogo (D).** Se exigen SKU, nombre, marca, categoría y PVP positivo para crear un candidato. Marca y categoría son necesarias para aplicar las tarifas generales; una ausencia no se inventa. El coste CSV se conserva como `Decimal` o como problema pendiente: una fila con coste ausente/inválido solo podrá ganar si F3 confirma una excepción XML válida para ese SKU y un precio final positivo. F2 no la cuenta aún como producto aceptado. IVA opcional se expresa como ratio (`21`, `21%` o `0,21` → `0.21`); peso opcional admite cero explícito, pero no negativos. La identidad de un duplicado *exacto* compara las 11 celdas originales; diferencias de texto que se normalicen igual siguen siendo un conflicto trazado, no se eliminan silenciosamente. La primera fila válida se determina **después** de validar el precio final de cada candidato en F3.

## Convenciones que afectan a las métricas

**Números.** `30,38` y `30.38` valen 30.38; `1.234,56` vale 1234.56; `1.234` aislado es ambiguo como dinero y se rechaza. Peso `1.997` se parsea como decimal, no como precio. Importes monetarios no aceptan notación exponencial. Descuento con `%` se divide por 100; sin `%`, valores menores que 1 son ratios y valores entre 1 y 100 son puntos porcentuales (`1` → 1%). Esta interpretación de `1` es D y deberá constar en la entrega. `2,0` como cantidad equivale a dos; `2,5` no se redondea. Coste neto unitario a cuatro decimales e importe de línea a dos, con `ROUND_HALF_UP`. Moneda EUR y base fiscal comparable son S pendientes.

**Tarifas.** La suma de descuentos de categoría y marca es D por la redacción del README. Ejemplo ficticio: coste 100, 10% y 5% → neto 85; la alternativa secuencial daría 85.5. Si la excepción de SKU es válida, se usa su precio sin otros descuentos. Excepción sin producto: `UNKNOWN_PRODUCT_SKU`. Una regla general inválida o contradictoria hace fallar la ejecución: ignorarla o elegir la primera produciría precios netos sin fundamento. Un descuento combinado que deje coste <=0 o una excepción de SKU inválida impiden cargar ese producto; no caer silenciosamente a otra regla. Los descuentos por volumen requieren cantidades de compra que las fuentes no aportan.

**Fechas y cabeceras.** Fecha de pedido con hora y fecha sin hora del mismo día son compatibles. Si falta fecha en una línea, heredar solo un día inequívoco de ese pedido y avisar (`HEADER_VALUE_INHERITED`). No rellenar precios o cantidades ausentes. Pedido con cabecera válida pero algunas líneas inválidas: cargar las válidas, marcarlo como parcial y registrar cada rechazo. Pedido sin líneas válidas: no cargar. Zona de negocio propuesta: Europe/Madrid, S por validar. `updated_at` de stock debe incluir zona horaria.

**Estados observados.** `COMPLETADO`, `Completado`, `completado` → COMPLETADO; `ENVIADO`, `enviado` → ENVIADO; `CANCELADO`, `cancelado` → CANCELADO; `PENDIENTE` → PENDIENTE; `DEVUELTO` → DEVUELTO. Canales observados `B2B`/`b2b` → B2B; `B2C`/`b2c` → B2C; `MARKETPLACE`/`Marketplace` → marketplace. No se han observado ni inventado más estados. D/S: facturación operativa incluye solo ENVIADO y COMPLETADO con líneas válidas positivas. Pendientes, cancelados y devueltos quedan fuera; una devolución positiva o negativa se conserva sin cambiarle el signo ni restarla automáticamente de una venta no vinculada. Esta definición debe mostrarse en SOLUCION y en el dashboard.

**Stock.** `stock_total` suma `quantity` de almacenes observados; `reserved` queda visible aparte y no se resta sin confirmar si el negocio quiere disponibilidad. Si `reserved > quantity`, registrar `RESERVED_EXCEEDS_QUANTITY` y conservar los valores: puede ser una reserva superior al físico, no necesariamente un error del proveedor. Si hay una observación inválida para un SKU conocido, el total de ese SKU queda `NULL` para evitar publicar una suma parcial. Ausencia de observaciones también es `NULL`, con motivo distinto. La API incompleta tras reintentos falla toda la ejecución. No se presupone que el dato ausente sea cero.

## Duplicados e idempotencia

Validar cada fila de catálogo, incluida la posibilidad de precio neto por excepción, antes de escoger ganador. Entre filas válidas del mismo SKU, conservar la primera en orden del CSV; las posteriores se registran como conflicto aunque tengan un precio mayor o una fecha de alta más reciente. Exactamente iguales se marcan como duplicado. Es una política reproducible y fácil de explicar; el origen no da fecha de actualización para escoger la «última». Si la primera fila del SKU es inválida, puede ganar la primera válida posterior.

Para líneas, usar una firma SHA-256 sobre valores normalizados, sin número físico de fila; almacenar una sola ocurrencia por firma y registrar repeticiones. Una línea corregida cambia de firma: el siguiente snapshot completo retira la antigua. Si el ERP proporciona ID de línea en el futuro, sustituir esta política. Repetir el ETL con las mismas fuentes deja iguales las tablas de negocio; las ejecuciones y sus incidencias de auditoría sí se añaden. Detalles transaccionales en TECH_SPEC y ADR 002.

## Rechazos y conteos

Cada incidencia registra `run_id`, fuente, fila de CSV o localizador XML/API, entidad/SKU o pedido si se conoce, `reason_code` estable, acción, detalle y payload original razonablemente acotado. Nunca guardar tokens o URL secreta de Make. Se admiten varios motivos por una misma fila. Códigos esenciales: `INVALID_COLUMN_COUNT`, `MISSING_REQUIRED_FIELD`, `INVALID_PRICE`, `NON_POSITIVE_PRICE`, `INVALID_EAN`, `UNSAFE_SCIENTIFIC_EAN`, `INVALID_DATE`, `INVALID_DISCOUNT`, `INVALID_QUANTITY`, `UNKNOWN_PRODUCT_SKU`, `CONFLICTING_PRODUCT_SKU`, `DUPLICATE_ORDER_LINE`, `INVALID_STOCK` y `STOCK_FETCH_FAILED`; los demás códigos de la matriz se incorporan solo si el caso aparece.

Por cada fuente y ejecución completada, contar registros de origen con una sola disposición final: `rows_read = rows_accepted + rows_rejected + rows_deduplicated`. Una fila inválida o un SKU conflictivo descartado suma en `rows_rejected`; un duplicado exacto o una línea repetida por firma suma en `rows_deduplicated`, **no** en `rows_rejected`. `quality_warnings` y `discarded_fields` son métricas adicionales de incidencias y no se suman a esa igualdad. La tabla `rejections` puede conservar todos esos motivos mediante su campo `action`; el nombre de la tabla no convierte un aviso o duplicado en fila rechazada.

Una fila rechazada cuenta una sola vez aunque tenga varios motivos. La distribución `rejected_by_reason` cuenta cada motivo de acción «rechazar», por lo que su suma puede superar `rows_rejected`; excluye deduplicaciones y avisos. Make usa `rows_rejected` para su umbral de calidad, nunca el número total de incidencias de la tabla. Una ejecución fallida se informa como fallida, nunca como éxito con ceros; no se exige la igualdad de filas para una fuente que no llegó a leerse por completo.
